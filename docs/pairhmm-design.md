# PairHMM kernel design

This note describes how `crates/pairhmm` computes GATK's read-versus-haplotype likelihoods and why it differs from Intel GKL's kernel.

## The model

The kernel computes exactly what GATK's Java `LoglessPairHMM` computes: the forward probability of a three-state pair HMM (match, insertion, deletion) over a read of length n and a haplotype of length m, in linear (not log) space, seeded with an initial deletion probability of `C / m` in every column of row zero so that the read may start anywhere in the haplotype, and summed over match and insertion states of the last row so that it may end anywhere. Transition probabilities depend only on the read position (insertion and deletion gap-open qualities and the gap-continuation penalty); emission priors depend on the read base quality and on whether the read base matches the haplotype base, with `N` matching everything and mismatches divided by three. All tables are built in double precision with the same quantized log-sum-exp approximation GATK uses, so the double-precision kernel reproduces GATK's Java results to within a few ulps and, in the HaplotypeCaller runs we have checked, produces byte-identical gVCFs. The scale constant is `2^1020` in double and `2^120` in single precision, and any single-precision result below `1e-28` is recomputed in double, which is Intel GKL's policy.

## Lane layout

GKL vectorizes inside one read-haplotype matrix along anti-diagonals, which needs cross-lane shifts, masks for the ramp-up and ramp-down of each anti-diagonal, and a fresh set of per-read tables for every pair. This kernel instead puts a different read in each SIMD lane and computes all lanes against one haplotype at a time. Every lane is independent, so the inner loop is pure multiply-add with no cross-lane operations, and it maps equally well to 4-lane NEON and 16-lane AVX-512. Reads are sorted by length so that the lanes of a batch have similar lengths; lanes whose read is shorter than the batch maximum see zero-padded tables, produce zeros, and are excluded from the result sum by a per-row mask. The number of hardware vectors ganged into one logical lane group is a per-backend constant chosen to cover the FMA latency of the one serial dependency in the recurrence (deletion along a row).

## Sweep order and memory

The matrix is swept row by row: read position outer, haplotype position inner. The six transition probabilities of the row stay in registers, the emission prior is a single load from a per-row table indexed by the haplotype base (five tables, `ACGTN`, plus one per other byte encountered), and only the previous row is read. The working set is two rows of three vectors per column, tens of kilobytes, so the kernel stays in L1 for typical haplotype lengths.

## Sharing work between haplotypes

Haplotypes in an assembly region are variants of one reference and share long common prefixes. Because column j of the matrix depends only on the first j haplotype bases and on the initial constant, two haplotypes with a common prefix of length p have identical columns 0 through p. The kernel sorts haplotypes lexicographically, computes the longest common prefix between consecutive ones, and starts each haplotype from a snapshot of the column where it diverges from its predecessor. Snapshots are taken only at columns some later haplotype will need, which follows from the LCP array, and a counting argument shows the last writer of a snapshot always shares the required prefix. GATK's Java implementation exploits the same prefix structure, but only between haplotypes of equal length, because the initial constant `C / m` depends on the length. Since the recurrence is linear in that constant, a snapshot computed for length m1 is reused for length m2 by multiplying it by `m1 / m2`, which is exact up to one rounding. Duplicate haplotypes and haplotypes that are prefixes of others cost nothing beyond the snapshot copy.

## Lane utilisation and per-call cost

Replaying GATK's own dumps of PairHMM inputs (with duplicate reads handled correctly, which an earlier version of the replay tool did not) shows that ordinary assembly regions hold about forty-six reads against three or four haplotypes, segmental-duplication hotspots about two hundred reads against sixty, and centromeres thousands of reads against a hundred. Kernel workspaces are cached per thread and sized without clearing them, because clearing every snapshot column per call was a third of the time on ordinary regions. On AVX-512 the reads of a region run in 32-lane batches with two lane groups, and a remainder of at most sixteen reads runs on a single 16-lane group rather than half-empty. The inner loop checks bounds once per row segment and reads and writes through raw pointers, which on NEON is worth 1.8x. On x86 the kernel runs with flush-to-zero and denormals-are-zero set (and the caller's MXCSR restored afterwards): single-precision DP values routinely reach the subnormal range, where x86 takes a microcode assist per operation, and without this the float kernel was ten times slower than double. All buffers are 64-byte aligned so no vector load crosses a cache line.

## Numerics

Single precision is used first. The lane's raw result is compared against `1e-28` after each haplotype, GKL's criterion; failing pairs are collected and recomputed with the double-precision kernel. A read that failed against a third or more of the haplotypes is recomputed against all of them in one prefix-shared sweep; the remaining pairs are grouped by haplotype and run one haplotype at a time. On a centromere region, where four percent of pairs fail, this halves what the recomputation costs. The double-precision kernel uses the same lane layout with half the lanes.

The x86 backends run with flush-to-zero and denormals-are-zero set, as GKL does; NEON keeps subnormals. The two therefore agree bit for bit on every pair except those whose result lies within about two log10 units of the `1e-28` threshold, where the mass flushed on x86 is no longer far below an ulp of the single-precision result: on the chromosome 4 centromere dump, 149 of 2.27 million above-threshold pairs differ between Linux arm64 and Linux x86, by at most `7e-8` log10, and none elsewhere. Double-precision results are byte-identical across the two, below-threshold pairs included. Between operating systems the last bit of `log10` differs for a fraction of a percent of pairs (libm), which is why `pairhmm-replay` also prints a checksum of the results rounded to `1e-6` and can write per-pair results for comparison. Setting `FPCR.FZ` around the NEON kernel would make single precision bit-identical across the two Linux targets; it is not done, since the difference is far inside the `1e-4` criterion.

Per-row power-of-two rescaling of the single-precision kernel, which would avoid the double pass, was implemented and rejected. The rows before a lane's first rescale hold that lane's mass far above any trigger, so they flush at `2^-126` exactly as the plain kernel does, and paths that end up contributing to a result near `2^-126` can pass through those rows (a real pair from chromosome 8 lost 0.7 percent that way). No exponent per row can hold both the mass at `2^112` and such paths at once, so the safe criterion for deep pairs stays a threshold on the result, which is GKL's policy. Prefix sharing makes it worse: a shared column written by a sweep in which the read matched well holds values that are tiny relative to that sweep's scale, and a later haplotype that shares only the prefix needs exactly those.

## Threading

None inside the library. Every call computes on the calling thread; a `PairHmm` value is immutable and can be shared by any number of threads. This keeps CPU accounting honest in pipelines that schedule one process per core and leaves parallelism to the caller.

## What GATK sees

`FgklPairHmm` implements `PairHMMNativeBinding`. It flattens the holder objects into six primitive arrays plus two offset tables on the Java side, makes one JNI call per likelihood matrix, copies the inputs into Rust memory (no JNI critical section is held while computing), and writes the results back with one array-region call. `maxNumberOfThreads` is accepted and ignored; `useDoublePrecision` selects the double kernel.

## Partially determined haplotypes (DRAGEN mode)

GATK's `LoglessPDPairHMM` extends the recurrence with three branch matrices and a per-column deletion state (`NORMAL`, `INSIDE_DEL`, `AFTER_DEL`) driven by per-base flags, plus SNP flags that let a read base match an alternate allele. `crates/pairhmm/src/pdhmm.rs` holds an exact scalar port of it as the oracle for a future vectorized PD kernel. Two properties of GATK's implementation constrain that kernel: the deletion state is carried from the end of each row into the next row, so a column's values depend on flags to its right and columns cannot be shared between haplotypes; and GATK itself disables its prefix-sharing optimisation for PD haplotypes, so the native semantics to match are a full computation per pair, which is also what GKL's PD kernel does. The lane layout, per-read tables and flush-to-zero handling of the plain kernel carry over unchanged; the inner loop gains three `max` operations per cell and a second set of row buffers.
